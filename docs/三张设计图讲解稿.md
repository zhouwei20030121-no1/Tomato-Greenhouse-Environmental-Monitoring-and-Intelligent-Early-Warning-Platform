# 番茄温室系统设计图讲解稿

讲解人 周玮 222022325052097

这三张图分别回答三个问题：业务流程图说明系统怎样帮助管理员完成一次工作；时序图说明这项工作在各个模块之间怎样传递；UML类图说明系统需要保存哪些对象、这些对象怎样关联。它们使用黑白标准符号，详细方案与图片独立保存，不属于系统业务页面。

## 图一 业务流程图

### 可直接讲述的介绍

老师，这张图展示的是平台从接入真实数据到完成一次预警处理的业务流程。先看图的上半部分：用户登录后，后端校验身份并区分角色。系统维护员负责数据导入、模型训练和历史回放；温室管理员负责查看环境、处理预警、使用助手及配置环境范围。系统按节点和源时间读取公开温室记录，完成排序、去重和质量标记，然后通过回放与逻辑网关形成连续观测。这里并不随机产生温湿度，界面里的传感器对应原数据中的27个真实LoRaWAN节点。流程首先判断观测是否有效、是否足够新鲜；数据有问题时，生成节点维护提示，避免把缺失当作环境异常。数据正常时，计算温度、湿度与空气VPD，并检查模型和过去两小时的窗口是否就绪。条件满足才运行GRU预测未来半小时，否则保留真实监测并说明预测暂停的原因。

接着看中间部分：平台依据管理员设置的范围判断持续偏离和预测偏离，把满足条件的变化合并成事件，并保存触发读数、规则和模型版本。管理员首页以可全屏的温室全景为主，点击节点才弹出具体读数；独立的节点与趋势页承担历史分析，不再重复首页。用户从悬浮入口或助手页提问后，RAG助手先检索当前节点与事件证据，再用BM25、TF-IDF、RRF和MMR选择相关资料，交给DeepSeek整理解释。下半部分的关键判断是“用户是否确认处理”：大模型只能给出检查建议，不能直接操作设备。用户确认后，系统才生成唯一指令，交给虚拟执行器模拟通风、开窗或遮阳，保存回执。最后管理员继续查看后续历史观测、写下处理记录，再关闭事件或者继续关注。模拟指令只改变虚拟设备日志，不改写真实环境数据，所以这张图体现的是管理工作闭环，而不是声称已经验证了真实控制效果。

### 指图顺序与符号

先从最上方的圆角起止框开始，经过身份验证和角色判断，再沿箭头向下看维护与业务两类路径。平行四边形表示读取数据或返回结果；矩形表示排序、计算、保存、检索和执行等处理；菱形表示需要选择分支的条件，分支旁标注“是”或“否”；带箭头实线表示流向。最后“继续回放”回到接入节点，说明系统持续监测而非只运行一次。若老师问系统的实际用处，可以指向“预警展示—人工确认—回执—复看”，强调管理员得到的是具体检查位置、触发依据和处理记录。

## 图二 核心处理时序图

### 可直接讲述的介绍

老师，第一张图解释工作步骤，这张时序图进一步说明每一步由谁完成。图的横向是系统维护员、温室管理员、前端工作台、API与权限模块、回放分析服务、数据库、RAG助手、DeepSeek和事件执行服务；时间从上往下推进。两种角色有各自的登录会话，登录成功后通过HttpOnly Cookie携带身份。维护员开始回放后，前端先经过API鉴权，再把回放参数交给后台服务，回放服务只读取不晚于当前事件时钟的真实记录，再把当前五分钟格点和输入窗口送到分析模块。分析模块在模型与窗口都有效时运行GRU，否则走“暂停预测”的分支，然后把实际预测和满足规则的预警证据写入数据库。页面查询只读取这些结果，刷新页面不会重复累计预警次数。

接下来的交互说明大模型并非简单调用接口。管理员点击节点或历史页时，前端只请求API，由API读取数据库，前端并不直接连接SQLite。管理员从悬浮入口或助手页提出问题后，前端带上节点、时间或事件上下文；RAG模块用受限制的数据查询读取实际记录，并完成双路检索、RRF融合和MMR去重。相关证据被编号后才发送给DeepSeek，模型返回解释时必须引用这些编号，系统再核对引用是否合法。如果接口不可用，就走图中的备用分支，用同样的证据生成本地模板，并在界面明确显示降级状态。最后一段是人工处理：管理员确认事件并选择动作，事件服务检查权限、状态和指令ID是否重复，再调用虚拟执行器、保存回执并进入待复看状态。后续读取和关单仍由管理员完成。两类账号还分别限制业务处理与维护操作，权限由后端检查，而不是仅隐藏菜单。

### 指图顺序与符号

左侧的小人代表系统外部的管理员；参与者名称下方的竖向虚线是生命线；生命线上细长的矩形是激活条，表示该参与者正在处理一次调用。带实心箭头的实线表示同步请求，带箭头的虚线表示返回消息；指回自身的箭头表示模块内部计算。标注alt的组合片段表示互斥条件分支，例如模型可用与不可用、DeepSeek成功与降级。讲解时先看回放和分析，再看RAG问答，最后看人工确认与执行，避免逐条念全部消息。

## 图三 UML核心类图

### 可直接讲述的介绍

老师，前两张图解释流程和协作，这张类图说明系统需要管理哪些核心对象。最上面的温室与节点建立包含关系，一个温室在本数据中关联27个节点。每个节点有自己的编号和相对布局，并对应多条Reading，也就是带源时间、温湿度、RSSI、SNR与质量标记的原始观测。Prediction独立表示模型预测，关联节点和ModelVersion；模型版本保存训练与验证边界、输入规格以及权重位置。这样可以明确区分“实际测到了什么”和“模型预测了什么”，并追溯预测由哪一版模型产生。

中间的AlertEvent是预警业务对象，保存类型、状态、触发证据和回放会话。它可以关联零条或多条Command，也就是经过确认的模拟处理指令。指令有唯一ID、动作、状态与回执时间，重复提交同一个ID不会重复执行。右侧的KnowledgeChunk保存可引用的知识片段及来源；HybridRetriever负责召回、融合和去重；EvidenceAssistant把检索结果与当前数据组织成回答，并校验证据引用。ForecastService负责读取窗口和模型并产生预测，EventService负责确认、执行和关闭。User与AuthSession保存账号身份及有效会话；AuthService负责登录、密码摘要核对和后端权限检查。ReplayService只允许维护员控制回放，EventService只允许管理员确认并执行处理，因此角色分工有后端约束。类图中的服务类表示模块职责，既可以由Python类实现，也可以由对应服务函数实现。完整物理数据库还包括数据源、指令日志、任务和配置等辅助表，因此这张图展示的是核心领域结构，具体字段与约束以数据库DDL和设计方案为准。这样的组织方式也方便扩展：以后替换数据源、预测模型或执行器时，可以保留其余业务对象和处理流程。

### 指图顺序与符号

每个类框从上到下分为类名、属性和方法区域；加号表示公开成员，减号表示内部成员；属性按“名称：类型”标注，方法按“名称（参数）：返回类型”理解。没有领域方法的实体保留空的方法区，不把数据库记录强行画成会执行操作的对象。关联旁的1、27、0..*是多重性，表示一个对象对应另一类对象的数量范围。空心菱形表示聚合，温室聚合节点；普通实线表示结构关联；虚线箭头表示使用依赖，例如预测服务依赖读数和模型版本。讲解可按“温室与节点—观测与预测—预警与指令—知识与助手—账号权限”五组依次进行。

## 三张图之间怎样衔接

业务流程图中的“预测”在时序图里展开为回放服务向预测服务发起调用，在类图里对应ForecastService、ModelVersion与Prediction。流程图中的“解释预警”在时序图中展开为检索、模型生成和引用校验，在类图里对应KnowledgeChunk、HybridRetriever和EvidenceAssistant。流程图中的“人工确认后执行”在时序图里展开为状态校验、幂等指令和回执，在类图里对应AlertEvent、Command与EventService。这样三张图描述的是同一套系统的不同角度。


## 最新界面与图的对应关系

首页的大幅温室全景对应流程图中的“查看温室全景”，点击节点弹窗和节点历史页对应时序图中的只读查询请求。两者是不同工作任务，不是重复页面。悬浮AI入口与完整助手页共享同一套RAG服务，不是两套大模型。浅色照片背景、磨砂面板、字号和文案属于视觉设计，不改变类之间的关系，因此图里不增加“背景图片”等无关类。设计资料只作为独立讲解文件，不在系统业务菜单中展示。
